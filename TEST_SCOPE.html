Purpose

Why we test this

Management decisions rest on the numbers in these reports: lead counts, pipeline value, units sold, collections. A wrong or inconsistent number is a business defect even when the page looks fine. The suite checks that every number on these pages is valid, that the same metric shows the same value everywhere it appears, and that totals and percentages add up.

We only read data. No test creates, edits or deletes anything in the CRM or the database.

Approach

Six kinds of checks

Valid values

Every KPI shows a real number: not blank, not "—", NaN, undefined or negative. Every table renders. Pages load with no JavaScript errors and no failed API calls.

UI matches API

The hub's snapshot cards must match the numbers the backend actually returned.

This shows whether a wrong value comes from the front end or the backend.

Same metric, same value

A metric that appears on several pages must show the same value on all of them (16 cases, listed below).

Math inside a page

Parts add up to totals and percentages are correct (8 cases).

Example: Scheduled − Received = Outstanding on Collection Reports.

List counts

On Leads: card = tab badge = pager = exported rows, and every tab and filter count adds up to the total (13 tests).

UI matches database Optional

KPI values compared with SQL counts on the QA PostgreSQL database (18 tests). Runs only when database access is set up.

Boundaries

In scope and out of scope

In scope

  • Correctness and consistency of every count, amount and percentage on the 13 pages above
  • Default period (This month) and default view
  • Leads list: tabs, status filter, Individual/Corporate chips, search, first-page pagination, Excel export row count
  • Navigation from the hub to each report module
  • JavaScript errors and failed API calls on report pages
  • UI against API responses, and UI against the database when access is set up

Out of scope

  • Creating, editing or deleting records
  • Other periods (Last month, custom ranges) and the "You and your team" / "Mine" views
  • Campaign filter, report-tab switching and per-panel exports on module pages
  • Charts and graphs (we read KPI cards and tables only)
  • Field-level accuracy of individual records (we check counts and totals)
  • Login and permissions, security, performance and load
  • Browsers other than Chromium, mobile layouts (tests use a 1440×900 desktop window), accessibility, visual design
  • Production. Tests run against QA only
Read before acting on results

Assumptions and known limits

Things that can cause a failure that isn't an app bug

  • Live data. QA data changes while tests run. A cross-page test reads pages one after another, so a record added in between can cause a one-off mismatch. Re-run before you log a defect.
  • Rounded display values. Amounts like "2.18B" are rounded on screen, so value comparisons allow 0.5% tolerance. Counts must match exactly.
  • Label-based locators. The app has no data-testid attributes, so tests find elements by their visible labels. Renaming a KPI or table heading breaks the test, not the feature. We've asked the developers for test IDs (see LOCATORS.md).
  • Login session. Tests reuse a saved login. When it expires, every test fails until someone logs in again.
  • Database checks are provisional. The SQL table and column names are first guesses until we map them to the real schema. DB-L-09 (My Leads) is skipped because it depends on who is logged in. Database access is not yet working; we're waiting on valid credentials.
Output

How results reach the team

Every run writes an Excel defect report to reports/CRM_Defect_Report_<date>_<time>.xlsx, with three sheets:

SheetContents
SummaryRun date, environment, pass/fail/skip totals, pass rate, defects by severity and module
DefectsOne row per failed case: defect ID, test case ID, module, page URL, severity (P1–P4), steps to reproduce, expected vs actual, observed values, screenshot, and Status / Assigned To / Dev Comments columns for developers
All ResultsEvery test case with its status, duration and a one-line failure summary

When sharing the report, send the test-results folder with it so the screenshot links work. A Playwright HTML report with traces is also available for debugging.

Running it

How to run the suite

  1. One-time setup: npm install, then npx playwright install chromium
  2. Save a login: npm run login, sign in to QA in the browser that opens, then close it
  3. Run everything: npm test (about 4 tests in parallel, headless)
  4. Run one area: npx playwright test consistency, or one case: npx playwright test -g "X-05"
  5. Optional database checks: fill in .env, then npm run db:check and npm run test:db
Source of truth for test wording, severity and steps: tests/test-catalog.ts. Locators: tests/locators.ts.
