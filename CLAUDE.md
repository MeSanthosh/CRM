# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Playwright + TypeScript suite that checks the counts and metrics shown in the QA CRM app (`https://qa-crm.asquareab.com`, overridable with `BASE_URL`). It covers the Reports & Analytics hub, 10 report modules, the Executive Dashboard and the Leads page. It does not test application source code; everything runs against the live QA site, so data changes between runs.

## Commands

```bash
npm install && npx playwright install chromium
npm run login                      # opens codegen; log in, close the browser → writes auth.json (needed by every test)
npm test                           # all tests, headless, 4 workers
npx playwright test consistency    # one spec file (filename filter)
npx playwright test -g "X-05"      # a single test, matched by its case ID in the title
npm run test:scenarios             # workbook scenarios only (@scenario); npm run test:core for the rest
npm run test:headed                # headed, 1 worker
npm run report                     # open the Playwright HTML report
npx tsc                            # type-check only (tsconfig has noEmit); there is no linter

# Optional PostgreSQL comparison (needs .env copied from .env.example)
npm run db:check                   # connectivity check
npm run db:discover                # writes db-schema.md (gitignored)
npm run test:db                    # tests/db.spec.ts; skipped automatically if PG* env vars are missing
```

Locator discovery: `npx playwright codegen https://qa-crm.asquareab.com --load-storage=auth.json`.

## Architecture

**Layers.** Specs never write selectors inline:
- `tests/locators.ts` is the single source of truth for routes (`ROUTES`), XPath builders (`XP`), and lists of labels (`HUB_SNAPSHOT`, `HUB_MODULES`, `REPORT_PAGES`, `DASHBOARD_KPIS`, `LEADS_TABS`). XPaths match elements by visible label text because the app has no `data-testid` attributes. When the UI changes, fix the locator here and keep `LOCATORS.md` (a human/Selenium reference copy) in sync.
- `tests/helpers.ts` holds the reading primitives: `open` (goto + wait for data), `kpi`/`kpiText` (picks the right KPI pattern for any page through `kpiLocator`), `tabBadge`, `listCount`, `tableRows`, `tableColumn`, `act` (click, then wait for the XHR it triggers), plus API capture (`collectJson`/`numbersIn`/`matchesApi`) and `watchErrors`.
- `parseNum` turns display strings like `"2.18B USD"`, `"1.23M"` and `"52.8%"` into numbers. Because of that rounding, value comparisons use a tolerance (about 0.5%; see `matchesApi` and `sameValue` in `tests/db.ts`). Counts are compared exactly.

**Data-driven tests.** Many tests are generated from tables:
- `tests/consistency-cases.ts` `SAME[]`: each X-NN case lists sources (page + KPI label, or page + table heading, which counts table rows) that must all show the same value. To add a cross-page check, add an entry here.
- `tests/db-queries.ts` `DB_CHECKS[]`: maps a UI source to SQL. Table and column names are **first guesses** until they are mapped from `db-schema.md`.
- `consistency.spec.ts` M-NN tests check the math within a single page (sums, percentages).

**Test IDs drive the Excel report.** Every test title must start with a case ID (`RA-01`, `X-05`, `M-03`, `RA-MOD-01`, `DB-L-10`, …). `reporter/excel-reporter.ts` reads the ID from the title (regex `^[A-Z]+(-[A-Z]+)*-\d+`) and looks up module, severity, steps and expected result through `caseInfo()` in `tests/test-catalog.ts`. **When you add a test, add a matching catalog entry** so its defect row has real steps. The reporter writes `reports/CRM_Defect_Report_<date>_<time>.xlsx` (or to `EXCEL_REPORT_DIR`) and embeds failure screenshots from `test-results/`. Values recorded with `test.info().annotations` appear in the report's "observed values" column.

**Conventions in specs:**
- Use `expect.soft` when a test checks several values, so one run reports all of them.
- Use `test.skip(cond, reason)` for data-dependent cases (for example, zero SPAs in the period).
- Report modules open on "Last 12 months", while the hub and dashboard always show "This month". Cross-page comparisons (`consistency.spec.ts`, scenarios) switch each module to "This month" before reading it.
- To check a new release for UI changes, compare the frontend bundle name in the page source (`assets/index-<hash>.js`) with the last one you explored. If it changed, re-explore the screens and diff the labels against `REPORT_PAGES` / `LEAD_REPORT_TABS` in `locators.ts`.

**Page tests (`tests/pages/` + `tests/modules/`): the Page Object Model layer, one spec per hub card.** `BasePage` provides KPI reads, error watching and broken-value checks. `ReportModulePage` adds the period, custom dates, filters, views, reset, tabs and `table(heading)` → `ReportTable` (rows, column sums, export) shared by the 10 `/reports/*` modules. There is one subclass per card, declaring its route, `filters` (by first option), `mainKpi` and named tables. `ExecutiveReportsPage` (the dashboard at `/`) and `ReportsHubPage` extend `BasePage` directly. Page objects take locator strings from `locators.ts`, so don't write selectors in page classes or specs. `pages/fixtures.ts` injects page objects as fixtures (`async ({ hub, sales }) => …`) and provides `expected('…')` for the report's Expected Result. `modules/checks.ts` holds the 11 common module checks; each spec calls them under its own IDs (`SAL-01`…`SAL-11`) and adds page-specific tests from `-12`. Each spec's describe is tagged `@pages` plus `@<page>-reports`; npm scripts `test:<page>-reports` run one page. The reporter maps the ID prefixes (HUB, LDR, SAL, INV, CUS, BRK, MKT, RES, SPA, COL, EXE, EXC) to `Page · <name>` through `PAGE_TESTS` in `test-catalog.ts`. A new page needs four things: a page class, a fixture, a spec, and an entry in `PAGE_TESTS` and the npm scripts.

**Workbook scenarios (`tests/scenarios/`).** The 133 scenarios in `Testcase/Reports_Analytics_Test_Scenarios.xlsx` are a separate layer from the core suite. `catalog.ts` reads the workbook at runtime, and test titles come from it through `sc(id)`. Declare each scenario with `scenario(id, expected, fn)` (tag `@scenario`, plus an `expected` annotation that the Excel reporter shows as the Expected Result) or with `manual(id, reason)` (Skipped, tag `@manual`). Every workbook ID must appear exactly once. The reporter maps `RA-###` IDs to the module `Scenario · <Test Area>`. Scenario tests set the report period explicitly with `openReport(page, path, period)`, because modules currently default to Last 12 months, not This month.

**Service Requests workbook (`tests/service-request/`).** This automates `Testcase/Service_Requests_Test_Cases.xlsx` for `/service-requests` (After-Sales). `catalog.ts` reads the sheet. It holds data only, because the reporter imports it. Declare tests with `test(...sr('SR-046'), …)` and Manual rows with `manual(id)` from `shared.ts`. `coverage.spec.ts` (SR-COV-01) fails when a sheet ID has no test. The page object `ServiceRequestsPage` (fixture `serviceRequests`) waits for `GET /service-requests` after every open, search or filter, then checks "Queue (N)" and the rows against that response. Its locators are `SR_XP` and its page texts are `SR_TEXT`, both in `locators.ts`. Only `lifecycle.spec.ts` writes data. It runs as `describe.serial`: SR-046 creates one `[AUTO]` ticket per run, and the later tests touch only that ticket (`SKIP_SR_WRITE_TESTS=true` skips them). Never change tickets the suite did not create. The reporter maps `SR-*` IDs to `Service Requests · <Area>`. `npm run test:core` excludes the `@service-requests` tag.

**Reports workbooks (`tests/reports/`).** This automates one workbook per report in `Testcase/Reports/` (`RPT-05_Lead_Register_Test_Cases.xlsx`, `RPT-01_…`, `RPT-03_…`, `RPT-23_…`, `RPT-21_…`; `catalog.ts` reads every `RPT-<nn>_*_Test_Cases.xlsx` there, and `REP-###` IDs must be unique across them), one block of `REP-###` cases per report in the redesigned Reports & Analytics catalogue (build v2.0 0411: category tabs and report cards such as "Open RPT-05 →"). `catalog.ts` reads the sheets (data only, because the reporter imports it); declare tests with `test(...rep('REP-005'), …)`; `coverage.spec.ts` (REP-COV-01) fails when a sheet ID has no test. Page objects: `ReportCatalogPage` (fixture `reportCatalog`), `SingleReportPage` configured by a `REP_TEXT` entry (fixture `leadRegister` for RPT-05), and `LeadsListPage` (fixture `leadsList`; `allLeads(tab)` reads every pager page of a tab plus the GET /leads items, `detail()` reads the Lead Detail dialog). `SingleReportPage` extends `ReportModulePage` (period, custom dates, All/Mine, Reset), finds filters by label (`filter('Project')`), and `data()` returns the report API response for the selection on screen (it records every response, because a repeated selection is served from cache). Mine hides the Salesperson filter (`hiddenParams()`). Locators are `REP_XP`, `LEADS_ROW` and `REP_TEXT` in `locators.ts`. Match report rows to a module by record ID, never by name. `lead-register.data.ts` turns Leads-module data into the expected records for any filter selection (period by captured/created date within the dates the report says it used, project = `preferredProjectCode`, salesperson = `assignedToUser`, Mine = Leads → My Leads); keep expected values derived like this, never hard-coded. RPT-01 Executive Dashboard (REP-028…056, fixture `executiveDashboard`) is a 5-row scorecard: `executive-dashboard.data.ts` derives each Current Actual for the selection from `CrmData` (fixture `crmData`: read-only GETs with the app's own session token for inventory units, contracts plus each contract's opportunity owner and broker, campaign budgets, and RPT-03 rates); executed SPAs = SIGNED contracts by signed date, commission = broker standard rate (+ Tier 1 bonus above the RPT-03 volume threshold) or 2% direct. REP-044 (Escrow) is Blocked: no receipts source is readable. RPT-03 Control & Assumptions Register (REP-057…082, fixture `controlAssumptions`) is configuration: `control-assumptions.data.ts` checks rows against the report's own methodology entries (`REP_XP.definitionItems`: stated base values, allowed Unit/Owner/Review lists, parameter count), the Inventory product rates (`CrmData.products()`) and RPT-01's stated broker rates, and expects the same register for every period, project, salesperson and view. RPT-23 Master Data Dictionary (REP-083…109, fixture `dataDictionary`) is checked the same way (`data-dictionary.data.ts`), plus its "Sheet NN" sources against catalogue report RPT-NN (`ReportCatalogPage.allCards()` reads every tab), its formulas against RPT-01's methodology, its unit count against Inventory and its fee against RPT-03; REP-096/097 take their expected result from the report's own description. RPT-21 Summary by Property Type (REP-110…136, fixture `propertySummary`, Inventory Reports) has a `<tfoot>` total row (`SingleReportPage.totalRow()`, `ReportData.totalRow`; `download()` returns it as `sheet.total`) and no Salesperson filter; `property-summary.data.ts` matches each category to an Inventory unit type by name and derives keys, net area, base value (net area × product rate) and executed SPAs per category. RPT-18 Revenue Management Engine (REP-137…164, fixture `revenueManagement`, workbook `RPT-18_Revenue_Management_Engine_Test_Cases.xlsx`): `revenue-management.data.ts` matches each sub-category to one Inventory product (type, sub-type, bedrooms, sqm), reads the demand bands from the methodology, takes the status → action rule from `REP_TEXT.revenueManagement.actions`, and bounds Actual Qtr Absorption between the quarter's executed SPAs and those plus confirmed reservations (`CrmData.reservations()`). RPT-16 Sales Funnel (REP-165…196, fixture `salesFunnel`, Sales Reports, filters Project / Salesperson / Broker (`brokerId`) / Campaign (`campaignId`)): `sales-funnel.data.ts` counts each stage from its module by the date the record entered it (leads captured, leads qualified, opportunities created, reservations, signed SPAs) using `CrmData.leads()` / `opportunities()`, taking project / owner / broker / campaign from the record, else its opportunity and lead. RPT-19 Smart Sales Forecast (REP-197…221, fixture `smartForecast`, Sales Reports, `<tfoot>` TOTAL FORECAST row): `smart-forecast.data.ts` reads the stated probability, price / absorption ranges, totals, horizon and KPI-06 from the methodology, bounds each month's pipeline volume by open opportunities with that expected close date (`CrmData.opportunities()` now has `probability` and `closeDay`), compares the probability with the pipeline average / budget-weighted probability / won ÷ (won + lost), and the price with the average base price of Available units (`Unit.availability`). RPT-20 Project Cash Flow Forecast (REP-222…246, fixture `cashFlow`, `<tfoot>` TOTAL CASH FLOW row): `cash-flow.data.ts` expects buyer inflows = signed SPAs' payment-plan lines by due month (`CrmData.paymentLines()` reads each contract's detail), broker commission = RPT-03 standard rate split by the timing the methodology states, and the opening escrow balance = receipts "Cleared in Escrow" in RPT-10 Buyer Payment Ledger (= RPT-01 Escrow Collections); REP-241/242 (dev and marketing outflows) are Blocked for lack of a source. Build `index-Dmirkzo4` (10-Nov-2026) hides the filter toolbar and All / Mine on RPT-01, 03, 23, 21, 18, 04, 16, 19 and 20 (`SingleReportPage.hasFilters()`; `selection()` / `data()` then ignore the period), drops the RPT-03, RPT-23, RPT-18 and RPT-04 cards from the catalogue (open them with the page object's `open()`), and sends back links to `/reports?cat=<category>`; the suites written before it still expect the filters and cards. The workbook is generated by a script (not in the repo); edit the xlsx directly or regenerate it. Run with `npm run test:reports` (note the trailing slash in its path filter, which keeps `tests/reports.spec.ts` out); `npm run test:core` excludes the `@reports-workbook` tag. The old hub tests (`tests/reports.spec.ts`, `HUB-*`, `RM-*`) still expect the pre-v2.0 module cards.

**Login.** The access token lasts 15 minutes and the app rotates its refresh token on use, so browsers that share one saved session log each other out once the token expires. Specs therefore import `test` from `tests/auth.ts` (which re-exports everything else from `@playwright/test`). Its `storageState` fixture gives each worker its own login in `.auth/worker-N.json` (gitignored), and logs in again when less than 3 minutes of the token are left. The login page asks for a database since v2.0; `login()` selects `CRM_DATABASE` (default `crm_qa`). `tests/global-setup.ts` still writes `auth.json`, which is used only when `CRM_USERNAME`/`CRM_PASSWORD` are missing. In a new spec, import `test` from `./auth` or `../auth`, never from `@playwright/test`. For an extra browser context, pass it the `storageState` fixture, not `auth.json`.

**Database safety.** Every DB connection (`tests/db.ts`, `scripts/pg.mjs`) runs `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY`. Keep it that way. Target the QA database only.

## Gotchas

- `auth.json`, `.env`, `reports/`, `test-results/` and `db-schema.md` are gitignored. If `auth.json` is missing or expired, every test fails at login. Re-run `npm run login`.
- On the Leads page the pager ("Page 1 of 25 · 615 leads") is hidden when there are 25 results or fewer. `listCount` then counts rows that contain `a.crm-record-link`.
- KPIs briefly show `—` (or `0` after a reload) while loading. Always read them through the helpers, which wait for a real value.
